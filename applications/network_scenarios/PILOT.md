# Proposed first paid pilot: repeated inventory-network scenarios

The intended customer already runs a stock-flow model many times to compare replenishment plans, supply interruptions or starting inventories. The first engagement should concentrate on one existing model, its regional reporting outputs and one operational decision. The deliverable is an imported model, a reusable compiled plan, reproducible full/reduced comparisons and scenario reports in the customer's existing workflow. This release is a prototype supporting that engagement, not evidence that a customer has bought it.

A suitable model has fixed nonnegative routing fractions, explicitly accounted exits, known replenishment distributions and useful regional aggregates. Frequent repeated scenario batches matter because compilation may cost more than the first full batch. Networks dominated by local constraints, demand caps or changing routing need additional work before this linear application is suitable. The diagnostic stock floor is not a capacity constraint and cannot be advertised as preventing stockouts.

The customer supplies a representative model, representative scenario batches and its existing baseline. Success means the requested outputs remain within the agreed tolerance, conservation is accounted for, useful stock-floor decisions agree, and total wall time over the agreed number of batches improves after including import, compilation, validation, encoding, report construction and integration overhead. The customer and developer should agree those numerical thresholds before the pilot. No fixed speedup is promised by the current synthetic receipts.

The evaluation should compare both the customer's actual tool and a strong sparse implementation. Where a hand aggregate already exists, include it: a compiler cannot claim credit for a recurrence the customer already uses. Benefits can include automation across many supplied models, removal of repeated manual aggregation work, and trustworthy identification of cases that need more state. Customer time saved is distinct from compute time saved and should be measured separately.

For K batches, define the measured benefit as K times baseline batch cost minus compilation, integration and K times compiled batch cost. Dollar savings require the customer's actual cost of compute and engineering time; no price or return follows from a speedup ratio alone. The benchmark's estimated break-even point assumes equally sized batches and stable execution costs, and is only a planning estimate. Use the customer's workload distribution for a purchasing decision.

The paid package could combine model ingestion, implementation support and a maintained integration. A recurring license or service becomes credible once repeated use and support needs are demonstrated. Keep the first scope narrow enough that both sides can inspect the result: one model family, named outputs, clear input semantics and an acceptance report. The next commercial development should follow a successful customer result, rather than adding unrelated features before establishing fit.
